# taishan：KT + SGLang 可复现验证研究计划

更新：2026-11-08（北京时间）。状态见[研究状态](RESEARCH_STATUS.md)，既有证据见[阶段成果](RESEARCH_OUTCOMES.md)。本计划是后续实验的设计，不表示基准已经运行。

## 目标与当前依据

把双路鲲鹏 920（128 核、4 NUMA、约 502 GiB 可见内存）和两张 64 GiB Ascend 910B4-1 的 taishan 建成 KT CPU 专家卸载与 SGLang NPU 后端的可复现验证机。先交付正确性、性能与资源数据，再根据实测瓶颈选代码改动或上游回归报告。性能改进必须在同一请求集上给出端到端对照；负结果和无法支持的配置也如实交付。

已知可用起点是[2026-11-04 部署](2026-11-04-taishan-deepseek-v4-flash/README.md)：KT `c9873312643b615a717832946fba0346e69ab035`、SGLang `ff46d660d16cbf11ef393c80cc6b3ab7f6259780`、固定镜像摘要、W8A8 NPU 权重、逐层 MXFP4 CPU 专家、每层 32 个 NPU 常驻专家、`--kt-threadpool-count 4`、`--kt-cpuinfer 96`、单请求、8192 token、图捕获。已有短请求和 SSE 验收，但没有持续吞吐、并发或长上下文基准。既有部署不是新版上游性能的替身。

## 第一阶段：固定单卡基线与回归包

在独立的日期目录中先写 `experiment-plan.md`，冻结以下内容：源码提交、容器镜像摘要、CANN/torch/torch_npu 版本、权重来源及文件校验清单、GGUF 审计清单、启动命令和全部实际参数、设备映射、CPU/NUMA 布局、后台负载、请求 JSON 与随机种子。权重可复用已核验的原文件；记录清单和验证方式，不必为每次运行重算数百 GB 哈希。原始服务作为固定对照，实验进程、端口、日志和状态文件独立；任何会影响原服务的资源争用都要记录。

| 场景 | 第一轮建议范围 | 判定重点 |
| --- | --- | --- |
| 功能与正确性 | 健康检查、图捕获日志、固定确定性聊天、SSE 内容和 `[DONE]`、停止原因、重启后相同检查 | 按项记录 Passed / Failed / Not run；短问答不当作系统准确率 |
| 单请求性能 | 短、中、接近当前 8192 上限的输入；分别选短输出与足够长的稳态解码输出 | TTFT、prefill 耗时、稳态 decode tokens/s、总时长；记录实际输入/输出 token 数，排除过早截断 |
| 稳定性 | 固定负载连续运行，并保留每次请求及失败 | 完成率、延迟分布、资源随时间变化及错误日志；预先写明运行时长和停止条件 |
| 资源 | 运行前、预热后、采样期与结束后的 CPU、各 NUMA 节点内存、进程 RSS/交换、HBM 和 NPU 利用率 | 识别 CPU 专家、内存、NPU 或调度瓶颈；采样工具开销单独说明 |

正式性能测量先预热，重复相同请求并保存逐次记录；报告 P50/P95、离散程度、完成数及失败数。TTFT 以客户端收到首个有效内容为准，另记服务端可提供的 prefill 指标；两者不能混称。稳态 decode 只统计生成阶段的有效 token，不能把总响应耗时倒算成生成速度。性能正式轮避免重型 profiler；profiling 另起诊断轮，解释机制而非代替端到端结果。

首轮不把并发和长上下文写成既有能力：当前 `--max-running-requests 1`、`--context-length 8192`。这两项先做配置与正确性可行性验证，成功后再单独测性能。长请求可能需要改变分块 prefill、常驻专家和显存参数，必须标出新配置，不能与 8192 基线混作同配置加速。若并发或长请求不支持，保留最小失败复现，不强行给吞吐数值。具体限制见[昇腾教程](../doc/en/DeepSeek-V4-Flash_tutorial_for_Ascend_NPU.md)。

第一阶段的交付为可重跑的请求驱动脚本、环境清单、原始响应及资源采样、逐项回归结果、汇总报告和明确限制。基准结果应能回答：单请求速度与稳定性如何，资源在哪里耗尽，哪些扩展场景可运行。未完成以上证据前不改默认调优参数。

## 第二阶段：根据基线选一个瓶颈验证

若 CPU 专家与内存路径占主要时间，先测 `4/96` 现有设置与少量单因素候选：总线程数、CPU 绑核、内存放置；同时记录跨 NUMA 访问、每节点带宽及 prefill/decode 分项。每次只改变一个因素，同日交替测量原配置与候选，检查输出和资源是否一致。只有稳定的端到端收益、明确适用硬件范围和回退办法，才考虑默认值或实现 PR。

另一候选是静态专家放置。[现有离线回放](2026-11-07-taishan-expert-cache-study/README.md)在 20 条受控请求中显示历史热度放置的路由覆盖率高于固定前 32 个，但尚无推理加速实测。若基线显示 CPU 专家是关键路径，应先扩大且隔离训练/测试请求集，再做静态放置服务级 A/B。动态 LRU/EWMA 的大量换入须先计入真实搬运、转换和同步成本；离线命中率不能当作加速比。第二阶段先选最有证据的一个问题，不同时启动完整 NUMA、缓存与算子矩阵。

## 后续方向的进入条件

- **SGLang 910B 回归**：固定旧版结果后，在独立环境逐个验证目标上游提交的镜像、W8A8 加载、MoE 路由、图捕获、SSE 和重启。失败时交最小复现、版本、日志和硬件信息；仅在定位到可修复缺陷后准备 PR。[910B 镜像议题](https://github.com/sgl-project/sglang/issues/44959)与[NPU 重构路线图](https://github.com/sgl-project/sglang/issues/46487)提供选题背景，不能替代兼容性实测。
- **第二张卡**：先比较单卡服务与双卡双实例的请求吞吐、尾延迟、主存带宽和 CPU 争用。当前卸载教程仅验证 TP=EP=1；双卡 TP/EP 先判定实现支持与正确性，再决定是否进入性能矩阵。

每个新实验在日期目录事先写清问题、最小矩阵、正确性门槛、预期时长、停止条件及原服务恢复检查。远端文件或服务变更须先取得用户同意；长时间采集按用户设备规则后台运行，保留状态与日志，不把启动视为完成。
