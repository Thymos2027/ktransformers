# taishan：KT + SGLang 可复现验证研究计划

更新：2026-11-26（北京时间）。状态见[研究状态](RESEARCH_STATUS.md)，既有证据见[阶段成果](RESEARCH_OUTCOMES.md)。各阶段是否完成以结果报告为准。

## 当前目标：从 TP1 基线寻找整台双 NPU 机器的最佳性能

2026-11-26 用户澄清：TP1 是可复现的起点，后续可以扩展到 TP2；最终目标是在这台双路 Kunpeng 920、4 NUMA、两张 64 GiB 910B4-1 的机器上提升 DS-V4-Flash 推理性能。TP1 和 TP2 都是候选，不能预先指定最终拓扑，也不能用旧配置下 TP2 的小幅收益排除后续优化空间。本节替代下文历史阶段中关于研究终点和执行顺序的描述，原始实验和证据保留。

以此前关注的单请求 TTFT、稳态 TPOT/decode 和整请求耗时为主线。按短提示长输出、长提示长输出分别选配置；并发总吞吐作为独立目标，在支持性检查通过后另测，不与单请求速度混成一个“最高性能”数字。不同场景可以有不同胜出配置。

### 数据复审后的优先级

详细依据与下一轮矩阵见[2026-11-26计划复审](2026-11-26-taishan-research-plan-review/REVIEW.md)。本次离线重算54条正式请求、20304个逐token事件，补充分窗TPOT：801输入的前64输出约77.7ms，513–1000输出约110.4ms。固定KT源码还显示CPU单NUMA分片引用GGUF mmap、多分片创建重排副本；32线程/1池与96线程/4池同时改变内存路径，不能作为纯线程数对照。

当前计划据此改为小型对照与条件分支，旧的全CPU矩阵、EP2必测步骤、TP2 streaming优先开发安排由本节替代。已有streaming长提示收益和TP1/TP2功能证据直接复用，不从头重做历史全矩阵。

### 阶段 0：复用证据并校准测量条件

固定已有镜像、KT/SGLang提交与权重，记录实际扩展和候选源码身份。复用原始输入和采集器，增加本轮条件下的TP1校准，不把旧64输出数据与新1000输出组成加速比。先核对context、prefill单块、full/SWA实际池和页对齐；容量变更独立列项，7K及16K/32K随后按门槛扩展。

已有固定历史/局部数值探针已采集并发现跨TP差异，不能写成尚未运行；其验收边界见原报告。完整logits定位继续作为可选诊断，运行/通信正确性、原始输出和内容完整性仍须检查。

### 阶段 1（R1）：TP1长输出与侧流最小对照

TP1/EP1/DP1、单请求、graph、K32、96线程/4池为共同起点；动态驻留关闭。比较普通hybrid、hybrid+侧流、streaming路径、streaming+侧流四组，固定144/4096输入、1000输出及缓存预算。streaming配套depool/dedup一起切换，明确是整条路径比较；低于阈值的144输入作为未执行streaming计算的控制，仍记录启动内存差异。

每档1预热+3正式，共32条性能请求（24正式/8预热）、四次配置加载，另做短自然EOS内容观察。记录全程TPOT及1–64、65–256、257–512、513–1000输出窗口，保留输出IDs/正文。单次加载内重复仅用于筛选，胜出候选另做独立启动确认。预计60–100分钟，具体以加载和预热为准；不将启动记为验收。

### 阶段 2（R2）：按诊断选择一个CPU或放置干预

正式轮关闭额外诊断；少量诊断步单独采集CPU执行、暴露等待、拷贝和NPU/host开销，先确认实装二进制支持计时并估计采集扰动，不重启曾失败的profiler自动停止流程。总CPU墙钟与NPU重叠区间不能重复相加，也不能从两份不同主机时钟直接相减。

- CPU执行/等待占比较大时，先比较4池内64/96线程；需要时再补32线程/4池。32线程/1池作为mmap与NUMA内存路径联合方案、64线程/2池作为另一分片方案，均有页放置或诊断依据后才进入。记录亲和性、numa_maps、RssAnon/RssFile/PSS与可获得的内存带宽，不以线程数代替有效带宽。
- 热点覆盖不足且CPU miss暴露时，在同K32下测静态热专家，热度集和验收请求按请求分离；不把20条历史回放命中率当端到端目标。
- CPU暴露等待较小时，转查NPU、拷贝和提交路径，停止无依据扩大CPU/热专家参数。

### 阶段 3（R3）：尽早用小对照验证第二张NPU

R1/R2得到可复现候选后，先比较TP1与现有注意力TP2/MoE TP2（EP1），保持逻辑专家IDs/K32、请求及缓存预算一致，并测HCCL和host等待。不等TP1所有参数搜索完；也不假定TP1最佳线程/侧流配置在TP2中自动最优。

双卡计算收益与容量收益分别报告：同专家集合检验并行节省能否抵消通信；只有热点miss和CPU暴露成本支持时才利用额外HBM增加热专家/K。现有EP2、前缀K64无提速依据，不能作为必跑步骤；DP-attention与双实例维持单请求主线低优先级，有新吞吐假设再进入。记录逻辑专家并集、每卡完整专家或分片形状，CPU沿用单执行器结构，不为各rank重复整套CPU线程池。

### 阶段 4：提前审查MTP；TP2 streaming适配按收益进入

[CANN recipes上游指南](https://github.com/hicann/cann-recipes-infer/blob/master/docs/integration/sglang/dsv4-flash-single-npu-moe-offload/dsv4_flash_single_card_inference_guide.md)提供多token权重复用和可选MTP。兼容性审查提前到早期：检查现有MTP权重、具体补丁、CANN/torch兼容及HBM预算，不以环境升级作为默认动作。可行后先在隔离环境做同K/同运行时的普通decode与2行MTP，确有收益再试4行、TP2；新环境必须有自己的普通decode对照，上游速度不作为本机承诺。MTP流式事件可能一次增长多个token，须适配采集器，不能沿用普通decode的每事件+1门槛。

TP2 streaming先评估是否能同时保留单卡长prefill收益并改善decode，以及归约、驻留、临时缓冲的改动和预算，再决定完整开发。当前版本不能仅改TP参数假定支持。实际逐层streaming、所需归约、graph重放、输出和容量通过后才计性能；任何静默回退不计为streaming。阈值1536/2048仅为待测候选，按输入/输出长度和总耗时选取，逐拓扑验证。

### 候选确认与执行边界

筛选中约5%的TPOT/总时长收益或约10%的TTFT收益可优先安排确认；这是研究资源分配尺度，不是显著性或硬性淘汰线。小收益若成本低且稳定仍保留，百分之一排名不直接触发复杂改造。一轮无稳定收益且相应暴露成本未减少，就保留负结果并停止扩展该分支；有新机制证据才重开。

胜出候选至少两次独立启动/配置及交错A/B，扩大不同提示，分别报告相对原TP1、优化TP1和同期TP2的收益。少样本只给中位数/范围，不提供有代表性的P95。JSON格式失败按既有用户规则作为观察，正文异常、缺失IDs/事件、通信和设备错误不能成为加速成绩。新通信/投机实现做必要局部合并和内容检查，不将完整logits定位设为所有性能实验前置。

## 目标与当前依据

把双路鲲鹏 920（128 核、4 NUMA、约 502 GiB 可见内存）和两张 64 GiB Ascend 910B4-1 的 taishan 建成 KT CPU 专家卸载与 SGLang NPU 后端的可复现验证机。先交付正确性、性能与资源数据，再根据实测瓶颈选代码改动或上游回归报告。性能改进必须在同一请求集上给出端到端对照；负结果和无法支持的配置也如实交付。

已知可用起点是[2026-11-04 部署](2026-11-04-taishan-deepseek-v4-flash/README.md)：KT `c9873312643b615a717832946fba0346e69ab035`、SGLang `ff46d660d16cbf11ef393c80cc6b3ab7f6259780`、固定镜像摘要、W8A8 NPU 权重、逐层 MXFP4 CPU 专家、每层 32 个 NPU 常驻专家、`--kt-threadpool-count 4`、`--kt-cpuinfer 96`、单请求、8192 token、图捕获。已有短请求和 SSE 验收，但没有持续吞吐、并发或长上下文基准。既有部署不是新版上游性能的替身。

## 第一阶段：固定单卡基线与回归包

在独立的日期目录中先写 `experiment-plan.md`，冻结以下内容：源码提交、容器镜像摘要、CANN/torch/torch_npu 版本、权重来源及文件校验清单、GGUF 审计清单、启动命令和全部实际参数、设备映射、CPU/NUMA 布局、后台负载、请求 JSON 与随机种子。权重可复用已核验的原文件；记录清单和验证方式，不必为每次运行重算数百 GB 哈希。原始服务作为固定对照，实验进程、端口、日志和状态文件独立；任何会影响原服务的资源争用都要记录。

| 场景 | 第一轮建议范围 | 判定重点 |
| --- | --- | --- |
| 功能与正确性 | 健康检查、图捕获日志、固定确定性聊天、SSE 内容和 `[DONE]`、停止原因、重启后相同检查 | 按项记录 Passed / Failed / Not run；短问答不当作系统准确率 |
| 单请求性能 | 短、中、接近当前 8192 上限的输入；分别选短输出与足够长的稳态解码输出 | TTFT、prefill 耗时、稳态 decode tokens/s、总时长；记录实际输入/输出 token 数，排除过早截断 |
| 稳定性 | 固定负载连续运行，并保留每次请求及失败 | 完成率、延迟分布、资源随时间变化及错误日志；预先写明运行时长和停止条件 |
| 资源 | 运行前、预热后、采样期与结束后的 CPU、各 NUMA 节点内存、进程 RSS/交换、HBM 和 NPU 利用率 | 识别 CPU 专家、内存、NPU 或调度瓶颈；采样工具开销单独说明 |

正式性能测量先预热，重复相同请求并保存逐次记录；报告 P50/P95、离散程度、完成数及失败数。TTFT 以客户端收到首个有效内容为准，另记服务端可提供的 prefill 指标；两者不能混称。稳态 decode 只统计生成阶段的有效 token，不能把总响应耗时倒算成生成速度。性能正式轮避免重型 profiler；profiling 另起诊断轮，解释机制而非代替端到端结果。

首轮不把并发和长上下文写成既有能力：当前 `--max-running-requests 1`、`--context-length 8192`。这两项先做配置与正确性可行性验证，成功后再单独测性能。长请求可能需要改变分块 prefill、常驻专家和显存参数，必须标出新配置，不能与 8192 基线混作同配置加速。若并发或长请求不支持，保留最小失败复现，不强行给吞吐数值。具体限制见[昇腾教程](../doc/en/DeepSeek-V4-Flash_tutorial_for_Ascend_NPU.md)。

第一阶段的交付为可重跑的请求驱动脚本、环境清单、原始响应及资源采样、逐项回归结果、汇总报告和明确限制。基准结果应能回答：单请求速度与稳定性如何，资源在哪里耗尽，哪些扩展场景可运行。未完成以上证据前不改默认调优参数。

## 第二阶段：根据基线选一个瓶颈验证

若 CPU 专家与内存路径占主要时间，先测 `4/96` 现有设置与少量单因素候选：总线程数、CPU 绑核、内存放置；同时记录跨 NUMA 访问、每节点带宽及 prefill/decode 分项。每次只改变一个因素，同日交替测量原配置与候选，检查输出和资源是否一致。只有稳定的端到端收益、明确适用硬件范围和回退办法，才考虑默认值或实现 PR。

另一候选是静态专家放置。[现有离线回放](2026-11-07-taishan-expert-cache-study/README.md)在 20 条受控请求中显示历史热度放置的路由覆盖率高于固定前 32 个，但尚无推理加速实测。若基线显示 CPU 专家是关键路径，应先扩大且隔离训练/测试请求集，再做静态放置服务级 A/B。动态 LRU/EWMA 的大量换入须先计入真实搬运、转换和同步成本；离线命中率不能当作加速比。第二阶段先选最有证据的一个问题，不同时启动完整 NUMA、缓存与算子矩阵。
