# 首轮中止：累计流式通知跳变被误判为token缺失

2026-11-26（北京时间）。运行`tp1-side-20261126-193957-first`于远端20:08:56结束为failed，cleanup_verified=true。本次排查核对了本地原始记录、14项远端文件SHA以及实部署SGLang输出代码；修复仅写入本地后续运行脚本，未修改失败run或远端、未重启实验。

## 直接原因

控制器在h1（普通hybrid+侧流，streaming与动态驻留均关闭）的4096输入预热请求中，收到999次累计token通知；计数唯一一次从524跳到526，第525个输出没有单独的通知时间。请求最终生成1000个原始输出ID，`completion_tokens=1000`、`finish_reason=length`、SSE `[DONE]`齐全，正文4120字符。

原`prefill_gate.validate_request()`要求通知计数列表必须严格等于`1..1000`，因此抛出`Aggregated, missing or invalid token events`，控制器失败即停。它把流式通知完整性和生成token完整性合并成一个硬条件，约束过严。旧单测只验证逐项+1和错误/缺失情况，没有覆盖合法的累计结果跳变。

| 观测 | 原始值 |

| 最后正常通知 | count524，90.783775秒 |
| 下一次通知 | count526，90.916123秒 |
| 原始输出ID数 / 最终计数 | 1000 / 1000 |
| 通知数 / 未单独观测的中间计数 | 999 / 1（525） |
| 客户端全程TPOT | 61.538206 ms/token |
| 客户端decode / 服务端decode_throughput | 16.250067 / 16.250341 token/s |
| 与H0的4条4K请求比较 | 原始输出IDs及正文SHA均相同 |

直接原因可由原冻结校验器在该记录上重现；修复后的校验器可离线核验该请求的真实首尾计时及四个窗口，不需要增加或插值任何时间戳。

## 为什么stream_interval=1仍会发生

实部署SGLang固定版本为ff46d660，`incremental_streaming_output=false`。`tokenizer_manager.py::_wait_one_response()`在1751–1766行先取出并清空等待队列，在非增量模式下选择`out_list[-1]`，因此多个输出排队时会返回最新的累计结果。调度器的stream_interval=1不保证HTTP客户端每个token都收到一次独立通知。

现场源码SHA为`ec78cdde77241bdc4c6e15d00a9988f7f17ed376dd572a5bea9203b608a0516b`，摘录及14项远端哈希在本机run下的`diagnostic-readback.json`。这说明接口允许累计计数跳变；没有当时的逐项队列trace，无法精确还原此次排队发生在哪次CPU调度或IPC处理，也不能据此归因于NPU5负载或侧流计算错误。

## 排除与状态边界

- 原始记录共13条请求：H0完整8条（6正式/2预热），H1短档完整4条（3正式/1预热）及4K预热1条；共有13000个原始输出ID、12999个通知。S0/S1没有启动，H1的4K正式请求未执行，四组矩阵未完成。

## 本地修复

1. 保留1000个真实整数输出ID、结束状态、正文异常检查；累计通知必须单调递增、首个为1、最后为1000、时间有效。首尾缺失、计数回退或输出缺失仍失败。
2. 内部计数跳变不再直接中止。全程TPOT继续用真实首尾通知时间和生成token数计算；记录每次跳变及未单独观测的计数，明确不能还原全部单token到达时间。
3. 分窗以累计token号查找端点，代替按通知数组下标定位。本次缺的是525，四个窗口边界均在，所以可直接计算；若缺少512等边界，该窗口为null，汇总注明有效样本数，不补造时间。
4. 流式执行审计与计时审计分开记录。旧控制器将任何计时错误也写为`streaming_audit.passed=false`，容易误导为streaming失败；后续将计时错误写入`timing_audit`，保留独立执行结果。
