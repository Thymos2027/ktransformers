# TP2 正确性验证：从短请求通过走向可审查的支持候选

建立：2026-11-12（北京时间）。状态：本地方案，尚未实现采集器或启动远端实验。承接[TP2 功能验收](../2026-11-10-taishan-tp2/REVIEW.md)、[TP1/TP2 速度对照](../2026-11-11-taishan-tp-speed/REVIEW.md)与[社区分享](https://github.com/kvcache-ai/ktransformers/pull/2157#issuecomment-6810709188)。

## 要回答的问题

相同输入的自由生成在 TP1、TP2 之间不同，可能来自浮点运算顺序与近似量化，也可能来自实现错误。输出一旦分叉，之后的 token 历史和专家路由也可能不同；继续比较整段生成文本无法定位最初原因。本轮先在完全相同的 token 历史下比较前向结果，再评价有标准答案的任务质量。

目标范围仅为现有 W8A8 + MXFP4 CPU 卸载、TP=2/EP=1、单请求。TP1 是同量化实现的对照，不是未量化模型的正确性真值。验证通过后优先考虑显式 opt-in 的实验支持候选；是否默认启用、扩大 TP/EP 范围或被上游接收，仍需单独评审。

## 固定条件与代码落点

复用 KT `c9873312643b615a717832946fba0346e69ab035`、SGLang `ff46d660d16cbf11ef393c80cc6b3ab7f6259780`、原已核验权重和环境镜像。固定前 32 个常驻专家、96 CPU 线程、4 个线程池、单请求、分块 prefill 512、总缓存上限 16384，关闭 streaming prefill、dynamic resident、side stream。不同时调优专家数、NUMA 或模型版本。

TP 门禁实际位于 [SGLang fork 的 kt_ep_wrapper.py](https://github.com/Pan-Boyi/sglang/blob/ff46d660d16cbf11ef393c80cc6b3ab7f6259780/python/sglang/srt/layers/moe/kt_ep_wrapper.py)，不是 KT 主仓中的同名支持开关。先在固定 fork 完成定位；提交代码前与维护者确认接收仓库和分支。若转向不同上游版本，记录迁移 diff 并重跑相关验证，不能用旧 fork 的数据直接替代。

该 wrapper 只由 rank 0 创建 CPU 专家执行器，并在 Ascend dispatcher 的 post-combine hook 中加入 CPU 输出。还需沿调用方核实随后归约的实际次数和位置；仅有 `cpu_owner=True/False` 日志不能证明 CPU 结果没有重复相加。

## A：最小数值诊断，先找首个分歧

先完成只读源码审查与本地采集器设计，再安排远端小规模探针。首批建议 8 条固定输入，包含之前两个已分叉的性能提示词，并覆盖中英文、算术、结构化输出与短代码。冻结 tokenizer、chat template、token ID、位置和 mask，保存每个请求的完整配置。

| 对照 | 目的 |
| --- | --- |
| TP1 eager 重复执行；必要时重复启动 | 测本配置自身的可重复性，检查采集器 |
| TP1 eager ↔ TP2 eager | 排查分片、量化与 CPU 合并引入的差异 |
| TP2 eager ↔ TP2 decode graph | 排查捕获、重放和 CPU 回调同步的差异 |
| TP1 eager ↔ TP1 decode graph | 为图路径提供单卡对照 |

先比较 prefill 后首个预测位置。再为每条输入冻结最多 32 个后续 token，所有配置按同一序列逐步推进 KV 状态；这是 teacher forcing，不让各配置自行生成不同的后续历史。序列来源与 SHA-256 在测量前冻结；可包含预先保存的 TP1、TP2 序列，避免只选一种生成路径。

必须分别证明 prefill 与实际 decode/replay 被测到。接口返回的 input logprobs 若来自整段 prefill，不能冒充增量 decode 图的数值验证。先核实固定 fork 的接口语义；不足时在隔离副本添加受控采集。图内诊断采用预分配缓冲与重放后的读取，避免在 capture 中随意加入 Python hook 或主机同步；诊断轮不作性能测量。

记录完整词表 logits 的有限性、最大/均方绝对误差、归一化误差及分布差异；将 logits 转 FP32 后做指标计算，同时保留原始 dtype。记录 top-1、top-k、参考 top-1/top-2 间隔与分歧位置。全词表指标需要完整分布，不能用截断 top-k 代算 KL；近零数值的相对误差不能单独用作通过门槛。

首个分歧用同一输入激活做模块对照，依次核查 attention、MoE 路由与权重、NPU 专家分片输出、CPU 专家输出、combine/reduce 后的层输出。记录专家 ID、权重和顺序；后层路由若已分叉，应先定位更早的激活差异。必要时固定相同路由做局部算子测试，分别覆盖只命中常驻专家、只命中卸载专家和两者混合，不通过擅自改为全 CPU 配置绕开现有支持限制。

重点检查 W8A8 权重及 scale 的分片轴与对应关系、CPU 输出是否只加入一次、两个 rank 的归约结果是否符合预期，以及图重放时缓冲是否复用或同步错误。出现 NaN/Inf、形状/分片不符、CPU 结果倍增或缺失等明确缺陷时停止扩大任务，先留下最小复现。

小样本阶段是诊断，不因重复可重现就断言正确。数值门槛需参考算子精度、归约方式和独立局部参考实现制定；不能一律套用 FP32 的 `1e-5`，也不能把 TP1 自身零波动等同于跨 TP 必须逐位一致。先用诊断集确定可解释的容差，再冻结门槛与独立验证集；超限不能事后放宽而不另立修订记录。当前未制定数值通过标准，因此不得把本阶段写为已通过。

## B：代表性任务，检查质量是否退化

数值诊断没有未解释的结构性错误后，先用 32 题做评测流程验收，再运行冻结的独立任务集。初始建议 128 题：数学与逻辑、知识选择题、代码单元测试、中英文材料检索/结构化提取各 32 题。正式题目、数据版本、许可、答案、评分器、模板和样本选择种子须在运行前落盘，诊断与试跑题不混入正式集。

两配置使用完全相同的题目、思考模式、采样与 token 预算；允许自然停止，不使用速度实验的 `ignore_eos=true`。先根据流程验收冻结各类预算与耗时估计。截断、超时、接口错误和无法解析的回答均单独记录，并按事前规则计分，不能静默删除后比较准确率。代码题用固定测试与受限执行环境，开放文本题尽量采用可复核的规则评分。

报告各类别与总体分数、逐题配对得失、失败原因及配对差值的不确定性。正式运行前确定可接受退化幅度与判定方法；样本不足以排除该幅度时标为证据不足，不能将“差异不显著”当作等价证明。128 题是第一轮规模建议，不是已获得维护者认可的支持门槛，必要时扩大样本或采用维护者指定的标准任务。

## C：形成支持候选的门槛

1. 固定历史的数值验证通过事前标准，首个分歧及关键局部路径有可解释证据，没有未解决的重复归约、分片或同步错误。
2. 独立任务评测达到预定质量门槛；若不确定性过大，如实保留缺口。
3. 同配置覆盖 prefill、增量 decode、图捕获/多次重放、SSE 结束、服务重启和清理。先保持已测短输入范围；更长请求需重新核对 SWA/indexer 等实际池容量，不能仅凭 context-length=8192 推定可运行。
4. 产出小范围候选 diff、可重复的回归用例、精简硬件证据和已知限制。默认 TP1 的回归、未 opt-in 时的拒绝行为与不支持的 TP/EP 门禁保留。

若某一步定位到缺陷，优先提交该缺陷的最小复现与修复；支持 PR 的范围随证据确定。速度提升不是正确性验收门槛，2%–3% 的既有观察也不作为本轮必须复现的目标。

## 执行与交付

本轮仅编写本地方案，没有访问或修改服务器。新的远端诊断文件、实验服务及临时停止原服务，按设备规则在执行前明确范围并征得同意；不把讨论方向本身视为已启动实验。

实际运行前先完成采集器审查、冻结请求与阈值、数据量/耗时估计和失败即停流程。复用独立容器与原服务恢复、NPU/风扇遥测和心跳保护；正常或软件失败后恢复原服务并验收，硬件/散热告警时保持停止。预计较长的任务脱离会话后台执行，留状态和日志，只做短暂启动核查。

交付为实验身份、固定 token 历史、数值采集与对比程序、局部定位记录、独立任务集及评分器、逐题结果、恢复记录与 `REVIEW.md`。只有实际运行并复核后才写成果；当前不自动发布新的 GitHub 评论或创建支持 PR。
