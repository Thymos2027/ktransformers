# 双实例 CPU 线程预算干预实验

建立：2026-11-08（北京时间）。[分层诊断](../2026-11-08-taishan-dual-instance-diagnosis/experiment-plan.md)已经完成原服务、第二实例空闲、第二实例单独、两实例同时及清理后恢复五阶段的采集。两实例各使用 96 个 CPU 推理线程时，单独 decode 约 15.6–15.9 tok/s，同时执行都约 1.25 tok/s；约 122 秒的并发阶段，系统 CPU PSI `some` 增加约 110 秒（约 90% 的观察窗口），未观察到换入/换出。KT worker pool 有自旋等待，96+96 线程数超过机器的 128 个物理核。这支持线程竞争假设，但不能单凭观察证明它是全部退化的唯一原因。

本轮只改变**第二实例**的 `DSV4_CPUINFER`：96 → 32，保持原服务的 96 线程、两张卡、模型、权重、图执行、每层 32 个 NPU 常驻专家、请求和客户端路径不变。执行同样的 A→B→C→D→E 五阶段和 64-token 输出，记录完整响应、CPU PSI、进程 CPU 时间、缺页、换页及 NUMA 分布。两实例 CPU 推理线程总数由 192 降至 128；第二实例单独速度可能因线程减少而下降，因此判断重点是**同时执行时的吞吐、两边延迟和 CPU PSI 是否明显改善**，并与第二实例单独阶段比较。

若 96+32 在相同请求上明显改善，支持线程过量及自旋等待造成的调度竞争；若仍严重退化，则需要进一步调查内存带宽、NUMA 或两实例共享运行时。此实验并未修复 KT，也不构成新的默认参数建议。任何数值均须以完成后的原始结果和第二实例清理记录验收。

入口：`python diagnose.py --output runs/first`，后台在本机运行。远端临时目录为 `/data/deploy/dsv4-20261104/dual-instance-thread-budget-20261108`，第二实例最多运行 60 分钟并在正常结束、失败或超时后清理；原服务不重启。用户已授权本轮查因实验。远端服务与文件的操作仅限此实验目录和第二实例。
