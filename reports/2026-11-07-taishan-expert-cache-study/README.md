# Taishan服务器专家路由与缓存策略实验

## 实验运行位置

本实验在**已有容器** `dsv4-kt-20261104` 中运行。核对时该容器的完整 ID 为
`4af07a6481494a84b930e530a12e83031852bc5adc88ab5c43c6cb4bfb0fe35f`，
因此 Docker 列表里不会出现新容器。

采集脚本在这个容器内另起一个独立的 SGLang **进程**，使用逻辑 NPU 1
（物理 910B4-1 设备 5）和容器内端口 18081。原服务仍使用逻辑 NPU 0 和端口
18080。实验进程在采集和回放结束后已停止；`status.json` 显示 `phase=complete`、
`completed=20`、`server_stopped=true`。核对时原服务健康检查返回 HTTP 200。

两个服务使用同一套 DeepSeek-V4-Flash W8A8 权重和 MXFP4 CPU 专家文件。
采集脚本依次发送 20 条确定性的**受控测试请求**，启用 SGLang 内置的
`per_pass` 专家分布记录器，导出每次前向传播的专家计数，再离线回放四种放置策略。
这些请求实际经过模型推理，但**不是线上真实用户流量**。

## 回放口径

记录共包含 1908 次前向传播：前 572 次（约 30%）用于统计历史热度，后 1336
次用于测试。模型有 43 层、每层 256 个专家，模拟每层常驻 32 个专家。

- `current_first_n`：每层固定放置编号最靠前的 32 个专家，对应本次服务的
  `kt_expert_placement_strategy='prefix'`、`kt_num_gpu_experts=32` 配置。
- `static_train_frequency`：按训练段的访问次数，为每层固定选择最热的 32 个专家。
- `dynamic_lru` 和 `dynamic_ewma`：每次前向传播后，每层最多替换 2 个专家；
  替换从**下一次**前向传播开始生效。两种动态策略从前 32 个专家开始测试。

| 策略 | 测试段路由命中率 | 解码阶段命中率 | 测试段换入次数 |
| --- | ---: | ---: | ---: |
| 当前固定前 32 个 | 12.87% | 12.65% | 0 |
| 按历史热度固定 32 个 | 39.65% | 38.67% | 0 |
| 动态 LRU | 57.88% | 66.10% | 81,276 |
| 动态 EWMA | 59.26% | 67.68% | 86,950 |

表中的命中率是**专家路由覆盖率**，不是推理加速比例。固定热度策略在这组
请求中明显优于当前的前缀放置。动态策略覆盖率更高，但换入次数非常多；
按单专家约 24 MiB 的原始 W8A8 权重粗算，两者分别对应约 1.86 TiB 和
1.99 TiB 的权重搬运需求。这只是根据换入次数计算的量级，**不是实测传输量**，
也没有计入权重格式转换、调度与同步成本。

## 对 decode 速度的进一步分析

测试段有 1322 次单 token decode 前向传播；每次经过 43 个 MoE 层、每层路由到
6 个专家，因此每个 token 有 258 次专家选择。根据路由命中数折算如下：

| 策略 | 每个 decode token 在 NPU 上的专家选择 | 每个 decode token 留在 CPU 的专家选择 |
| --- | ---: | ---: |
| 当前固定前 32 个 | 32.64 | 225.36 |
| 按历史热度固定 32 个 | 99.78 | 158.22 |
| 动态 LRU | 170.53 | 87.47 |
| 动态 EWMA | 174.58 | 83.42 |

因此 LRU 比历史热度固定策略每个 decode token 平均多覆盖约 70.75 次专家选择。
但它在 decode 阶段共换入 80,072 次，平均每 token 约 60.57 次；EWMA
共换入 85,746 次，平均约 64.86 次。测试段的总换入次数还包括少量 prefill。

这些数字不能直接换算为 token/s：同一层的 CPU 专家可能并行执行，NPU
和 CPU 的工作也可能重叠，层间还存在串行依赖；一次 W8A8 换入需要从主存
搬运权重，并可能涉及格式转换和同步。当前四种策略仅做了**离线路由回放**，
没有实际运行动态 LRU/EWMA 服务，因此没有它们的 decode 延迟实测值。
判断 LRU 是否提速，需要逐层测量 CPU 耗时减少、NPU 耗时变化和权重换入
耗时，再在同一请求集上做服务级 A/B 测试。

20 条测试请求的数量很少，且多数输出在 96 token 上限处截断；目前不能把
这些命中率外推到生产流量。`replay.py` 尚未计入 W8A8 权重传输时间、CPU
执行 MXFP4 专家时间或 NPU 执行 W8A8 专家时间，因此不能由此推算 token/s
收益或判断动态换入是否划算。

## 单专家搬运微基准与结论范围

在空闲的第二张 NPU 上，从实际 W8A8 检查点读取第 0 层第 0 个专家的三组
权重和缩放因子，共 24.03125 MiB，重复 30 次，向预分配的 NPU 缓冲区拷贝：

| 主存来源 | 中位耗时 | P95 耗时 |
| --- | ---: | ---: |
| 普通内存 | 3.661 ms | 4.045 ms |
| 锁页内存 | 1.206 ms | 1.285 ms |

这是独立的主存到 NPU 拷贝微基准，**不等于服务内完整换入耗时**；它没有
包括专家索引更新、权重布局转换、缓存一致性、调度或与 CPU/NPU 计算重叠。
尚未测量 CPU MXFP4 与 NPU W8A8 专家的执行耗时，也没有实测动态策略的
decode token/s。因此本实验只能证明这组请求中的路由覆盖变化，不能断言
动态调度能提速。实验到此归档，后续若重启研究，应先取得更具代表性的流量，
再做相同请求的端到端 A/B 测试。
