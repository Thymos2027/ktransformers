# TP=2 相对 TP=1：本轮生成速度小幅提高约 2%–3%

验收：2026-11-11（北京时间）。运行 `speed-20261111-graph-check` 的四次启动、24 条正式请求和原服务恢复全部完成。对相同输入、固定 512 输出 token 的两种负载，TP=2 的生成速度中位数比 TP=1 高 **3.37% / 2.23%**，请求总耗时中位数减少 **2.87% / 1.55%**。首内容时间没有改善。跨 TP 的生成文本不同，此结论限于同输入、同输出 token 数的负载，不能称为相同输出或数值等价条件下的纯 TP 加速。

事前条件见[实验计划](experiment-plan.md)，独立复核结果见[result-summary.json](result-summary.json)。所有性能请求都达到了 512 token，没有用提前结束的响应计算提速。

## 结果

表中每项为同一 TP 配置六次正式请求的中位数，来自两次独立启动。百分比按两配置中位数之比计算，不混用配对比值的中位数。

| 实际输入 / 输出 token | TP1 decode | TP2 decode | decode 增幅 | TP1 / TP2 总时长 | 总耗时减少 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 144 / 512 | 15.329 tok/s | 15.845 tok/s | **3.37%** | 35.752 / 34.726 s | **2.87%** |
| 792 / 512 | 15.381 tok/s | 15.724 tok/s | **2.23%** | 44.489 / 43.797 s | **1.55%** |

| 实际输入 token | TP1 TTFT | TP2 TTFT | TP1 decode 范围 | TP2 decode 范围 |
| ---: | ---: | ---: | ---: | ---: |
| 144 | 2.423 s | 2.474 s | 15.258–15.423 tok/s | 15.616–16.000 tok/s |
| 792 | 11.275 s | 11.296 s | 15.344–15.401 tok/s | 15.524–15.944 tok/s |

TTFT 为远端同一 HTTP 客户端发出请求到首个非空 SSE 内容的时间，包含调度、prefill 和接口开销；本轮未单独测服务端 prefill。decode 按 `(512 - 1) / (末内容时间 - 首内容时间)` 计算；全部 32 次性能请求（含预热）各有 512 个内容事件，原始时间戳单调，复算与自动汇总一致。加载、图捕获、短任务门槛和预热都不纳入正式时长。

## 独立启动与波动

按 TP1a → TP2a → TP2b → TP1b 的 ABBA 顺序，分别配对首组 AB 与末组 BA。下表是每个启动内三次正式请求的速度中位数。

| 组别 | 输入 token | TP1 | TP2 | 增幅 |
| --- | ---: | ---: | ---: | ---: |
| TP1a / TP2a | 144 | 15.399 | 15.990 | 3.84% |
| TP1b / TP2b | 144 | 15.270 | 15.680 | 2.69% |
| TP1a / TP2a | 792 | 15.380 | 15.933 | 3.60% |
| TP1b / TP2b | 792 | 15.383 | 15.561 | 1.16% |

相同输入与重复编号的 12 个请求配对均为 TP2 较快，两次独立启动组方向一致。但每种 TP 只有两次独立启动，六个同长度请求不是六次独立硬件会话；较长输入的组间收益从 3.60% 变为 1.16%，不能把总体中位数解释为普遍、精确的固定加速率。这里记录小幅观察提升，不作统计显著性或其他请求上的承诺。

## 实验身份与质量边界

两配置使用同一固定镜像 `sha256:f03917b88b3696659b70e2e11c3190978af4732d87be05fc624245b9bb6f6b3e`、相同隔离 SGLang 候选、W8A8 与 MXFP4 文件、前 32 个 NPU 常驻专家、96 CPU 推理线程和 4 个线程池。上下文配置 8192、总缓存上限 16384、单请求、分块 prefill 512、decode 图、CPU 自动亲和性关闭；TP2 使用两卡，EP=1。未增加 TP2 的常驻专家数量，因此本轮回答的是固定专家集合下的 TP 速度。

四次启动的 20 项任务门槛全部通过，包括 `巴黎`、`42`、`156`、`READY` 和排序 JSON；对应 rank 的 decode 图均完成。24 条正式请求和 8 条预热都有正确的 prompt usage、512 completion token、`finish_reason=length` 与 SSE `[DONE]`。

同一输入在同一 TP 配置内的六次正式输出 SHA-256 一致，跨 TP 则全部不同。固定长度的工程说明负载可能有不同专家路由和内容计算，不能由这份速度数据排除该混杂，也没有验证完整 logits 或任务准确率等价。`ignore_eos=true` 与合成重复输入用于控制测量长度，不能代表自然停止的真实会话。未覆盖长上下文、并发、更多常驻专家或新上游版本。

TP2 仍仅由 rank 0 的同一 CPU 专家执行器计算卸载部分。小幅收益与 CPU 执行未被双卡同时分担的运行结构相符，但本轮没有服务端分项计时，不能据此认定性能瓶颈的精确占比或把差值全归因于 NPU。

## 资源、保护与恢复

TP1 的物理 NPU 2 HBM 在请求前后约为 47,586→47,691 MiB；TP2 两卡约为 27,204/27,147→27,312/27,235 MiB。TP2 减少每张卡占用并增加两卡运行时总开销；这些是设备总量快照，不能与未限制缓存容量的旧单卡基线直接计算显存节省率。主机交换区已用量约 28–29 MB，各启动前后未见大幅增长；这些稀疏快照不足以判定瞬时内存带宽或活跃换页。

本机 339 个有效热采样，两卡最高为 64°C/60°C，风扇最低 7425 RPM。一次读取状态的 SSH 超时，连续缺测计数为 1，未触发中止。四个实验容器均在完成测量后主动停止，仍有与前次相同的退出堆栈及退出码 137；服务期间未发现异常堆栈或 OOM，不能把最终停止写为优雅退出已验证。
