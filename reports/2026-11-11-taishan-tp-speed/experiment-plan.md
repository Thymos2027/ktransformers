# TP=2 相对 TP=1：固定条件的速度对照

建立日期：2026-11-11（北京时间）。用户已授权在原 TP 试跑基础上比较速度，包含临时停原服务、独立实验容器和结束后恢复。本实验承接[TP=2 功能验收](../2026-11-10-taishan-tp2/REVIEW.md)，回答相同专家常驻量、请求与缓存设置下，双卡张量并行是否改善单请求生成速度或延迟。

最终验收：修正版 `speed-20261111-graph-check` 已完成 24 条正式请求及原服务恢复。TP2 的生成速度中位数提高 3.37%/2.23%，总时长减少 2.87%/1.55%；跨 TP 输出不同，结论限于同输入同长度负载，详见[结果报告](REVIEW.md)和[复核摘要](result-summary.json)。以下保留事前协议及当时的启动记录。

## 固定项与唯一主要变量

| 项目 | 固定设置 |
| --- | --- |
| 模型与量化 | 同一 DeepSeek-V4-Flash W8A8 + 43 层 MXFP4 CPU 专家，不换文件 |
| 环境 | 已验收镜像 `sha256:f03917b88b3696659b70e2e11c3190978af4732d87be05fc624245b9bb6f6b3e`；同一隔离候选 SGLang `ff46d660...` |
| 专家与 CPU | 相同前 32 个常驻专家；4 个 KT 线程池、96 CPU 推理线程；TP=2 仍仅 rank 0 运行 CPU wrapper |
| 缓存与调度 | 总缓存 token 上限 16384、上下文配置 8192、单请求、分块 prefill 512、page=128、mem fraction=0.81；关闭 radix cache |
| 执行模式 | 两配置都启用 batch=1 decode 图，关闭 streaming prefill/dynamic resident/side stream；CPU 自动亲和性均关闭 |
| 采样 | 温度 0、seed=20261111、512 输出 token、`ignore_eos=true` |
| 变量 | TP=1 只用逻辑 NPU 0；TP=2 用逻辑 NPU 0/1；EP 均为 1，A2A backend 均为 none |

不与先前未限制总缓存容量的原服务耗时直接作速度比，也不在 TP=2 增加常驻专家。输出固定 512 token 用于稳定生成测量；忽略 EOS 后的输出只代表吞吐负载，不作为质量判断。

## 请求、门槛与重复方式

[requests.json](requests.json) 是在原服务 `/tokenize` 冻结的完整提示词、token ID 和 token 数。两条工程说明提示词实际长度为 144 和 792 token，加 512 输出后均在本候选 SWA 池的 1536 token 范围内；这是短输入/长生成对照，不是长上下文能力验证。

按 `tp1a → tp2a → tp2b → tp1b` 的 ABBA 顺序独立启动四个进程。每次启动都必须完成健康检查、对应 rank 的 decode 图捕获，以及 `巴黎`、`42`、`156`、`READY` 和排序 JSON 五项任务门槛。它们是有限的任务/接口检查，未代替完整 logits 等价或系统准确率评测。

每次启动的每个输入先预热一次，然后正式重复三次，共 24 条正式请求（每种 TP 各 12 条，每输入每 TP 六次，来自两次独立启动）和 8 条预热请求。每次核对实际 prompt token/ID、输出 512 token、`finish_reason=length`、usage 和 SSE `[DONE]`；不达门槛即停止，不自动降输出长度或剔除慢样本。

## 指标和判断

首内容时间 TTFT、末内容时间、请求总时长均在远端同一客户端进程用单调时钟计时。客户端观察到的 decode 速度定义为 `(completion_tokens - 1) / (末内容时间 - 首内容时间)`；保留每个 SSE 内容块时间以复核聚合影响。TTFT 包含调度与 prefill 等环节，不当作服务端单独 prefill 时间。

报告逐次值、中位数、范围、两次独立启动的分组结果，另按相同输入和重复编号配对 AB 与 BA：decode 比为 TP2/TP1，耗时改善比为 TP1/TP2，大于 1 表示 TP2 较快。六个请求配对嵌套于两次独立启动，不能当六组独立硬件会话做强统计推断。小于或接近运行波动的差异记为未测出稳定提升，不以单次最好结果决定。

输出全文及 SHA-256 保留；不同 TP 可能产生不同文本，即使 token 数相同也不宣称数值等价。若跨 TP 输出不同，速度结论仅限同输入、同长度采样负载。三组短任务和完整固定长度响应也不足以给生产质量背书。

## 执行、资源与恢复

本机 [`run_guarded.py`](run_guarded.py) 复用上一轮两侧热保护，打包并冻结本次远端控制器、公共运行时、工作负载与 launcher；上传副本保存在运行目录。远端 `remote_controller.py` nohup 脱离 SSH 会话，复用固定镜像并准备独立源码，顺序执行四轮后停止实验容器、恢复原单卡服务并检查短请求。

两卡必须可见、`OK`、低于 70°C，四风扇不低于 4500 RPM；连续两次遥测失败或本机心跳过期则停止模型，不自动恢复加载。各启动前后保存主存/NUMA/HBM 快照，后台持续保留热采样，不在正式轮开重型 profiler。正常结束或软件失败恢复原服务；硬件/热保护中止时保持停止。

预计约 40–70 分钟；性能测量最长 3 小时，异常超时后为恢复留 30 分钟。状态、逐次数据、stdout/stderr、两侧遥测均写入可查看目录；后台启动后只短暂检查，不持续守候。最终数据需由后续验收确认，不把启动或自动汇总当作速度结论。
