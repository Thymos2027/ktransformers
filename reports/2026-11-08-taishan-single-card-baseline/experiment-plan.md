# taishan 固定单卡基线：首轮实验计划

建立时间：2026-11-08（北京时间）。总体目标与指标定义见[研究计划](../RESEARCH_PLAN.md)。本目录保存本轮脚本和结果；脚本启动并不代表实验验收完成。

## 范围与环境

本轮只向现有 `192.168.137.11:18080` 服务发送顺序请求，不修改服务器文件、容器或服务配置。该服务的部署版本与模型来源见[部署报告](../2026-11-04-taishan-deepseek-v4-flash/README.md)。运行前只读核查：2026-11-08 10:42 北京时间容器 `dsv4-kt-20261104` 已运行 4 天，物理 NPU 2 有模型进程，物理 NPU 5 无模型进程；`/health`、`/v1/models`、`/tokenize` 与流式 usage 可用。主机内存约 502 GiB，交换分区 8 GiB 已基本用满；资源状态会随时间变化，不能把这次快照当正式基准结果。

## 请求和门槛

1. 健康检查与模型身份核对；记录 `/v1/models` 的 `max_model_len`，不得超过当前 8192 的部署限制。
2. 两条确定性短问答与一条 SSE 结束检查作为正确性门槛。实际输出、usage、结束原因和 `[DONE]` 都写入结果；失败时停止正式轮。
3. 用 `/tokenize` 把三个合成提示词分别调至约 128、2048、6144 输入 token；记录实际 token 数和完整提示词。它们是可复现的长度探针，不代表真实业务流量。每条生成上限 256 token，温度 0，先预热，再各重复 3 次，顺序固定。输出不足、截断和响应差异均保留，不择优剔除。
4. 每个正式请求记录客户端首个有效内容时间（TTFT）、末个内容时间、SSE 结束时间、服务端 usage、结束原因及响应文本。用 `completion_tokens - 1` 与首、末内容时间差计算客户端观察到的 decode 速度；若服务端把多个 token 合在一个 SSE 事件中，该指标仍可作为请求级速度，不能当逐 token 设备耗时。服务端 prefill 耗时若没有单独指标，报告为未测，不把 TTFT 等同于它。
5. 运行前后与各长度组前后，使用 SSH 只读采集 `free`、`numastat -m`、`npu-smi info` 和容器统计；采样会产生轻微观察开销，正式请求期间不运行重型 profiler。

正式轮结果记录 P50/P95、原始逐次值、失败数、实际 token 数和资源快照。单请求顺序实验不产生并发吞吐结论。`max_tokens` 截断的答案仍可用于生成速度测量，但不能用作质量通过证据。

## 执行和停止条件

入口：`python baseline.py --output runs/first`。脚本在本机写入 `status.json`、`events.jsonl`、`summary.json`、`requests.json`、`resources.jsonl`；错误保留在状态与日志。远端操作仅限已授权的 API 请求和只读 SSH 命令。预计运行超过短交互时，按设备规则用隐藏的独立 Windows 进程启动，标准输出与错误分别归档，启动后只做短暂存活检查。客户端进程退出后，再读取结果并完成验收；不将后台启动当作成功。

请求或正确性失败、健康检查异常、提示词达到当前模型长度上限、服务器负载显著被其他进程污染，均停止或将结果标为不可比较。现有服务不重启，因此图捕获**重启后**回归、长上下文、并发及第二张卡不属于本轮已验证范围；涉及远端文件或服务改动前先取得用户同意。
