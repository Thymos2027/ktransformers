## 单请求结果

现有 KT `c9873312643b615a717832946fba0346e69ab035`、SGLang `ff46d660d16cbf11ef393c80cc6b3ab7f6259780` 部署：一张 910B4-1、每层 32 个 NPU 常驻专家、`--kt-threadpool-count 4`、`--kt-cpuinfer 96`、单请求、8192 token、图捕获。输入是重复技术段落构成的长度探针，温度 0、最多生成 256 token；实际输出都自然停止，长度不同。以下为三次正式请求的中位数，括号内为最小值至最大值。

| 实际输入 / 输出 token | 首内容时间 TTFT | 请求总时长 | 客户端观察到的生成速度 |
| ---: | ---: | ---: | ---: |
| 149 / 249 | 2.469 s（2.469–2.484） | 18.375 s（18.344–18.375） | 15.668 tok/s（15.653–15.699） |
| 2066 / 111 | 28.609 s（28.593–28.609） | 35.719 s（35.718–35.719） | 15.643 tok/s（15.574–15.645） |
| 6170 / 157 | 83.844 s（83.781–83.860） | 93.891 s（93.828–93.922） | 15.649 tok/s（15.625–15.649） |

TTFT 为客户端发请求至首个非空 SSE `content` 的时间。生成速度按 `(completion_tokens - 1) / (末个内容时间 - 首个内容时间)` 计算；服务端 usage 提供 token 数，SSE 中若多个 token 合并发送，此值仍是请求级观察速度，不能当逐 token NPU 算子速度。服务端单独的 prefill 耗时**未采到**，不能把 TTFT 直接称作 prefill 时间。每组只有三次，P95 统计意义很弱，因此展示原始范围。

首内容等待随输入长度增长明显：149 到 6170 token 的中位 TTFT 从 2.469 增至 83.844 秒，跨三个点的观察斜率约 13.5 ms/输入 token。这只是本配置和合成请求的现象，包含 HTTP、调度与 prefill 等时间，尚未定位原因。三个输入长度的生成速度均在约 15.6 tok/s。由于各组输出分别为 249、111、157 token，**请求总时长不能直接当作相同输出长度的 prefill 对照**。首个 149-token 预热请求 TTFT 为 7.66 秒、总时长 25.48 秒，明显慢于随后的正式轮；原因未确定，报告未将它纳入正式中位数。

## 资源观察与限制

八次只读快照均成功。前后主机可用内存约 382.38→381.92 GB；容器统计约 209.5→210.1 GiB（含容器计费的缓存等，不等于专家权重精确 RSS）；物理 NPU 2 的 HBM 约 57,631→57,650 MiB，另一张卡约 3,403→3,402 MiB。交换分区已用量约 8.51→7.95 GB，实验期间未见持续增长。这些稀疏快照不能判断瞬时带宽、NPU 利用率、CPU 专家耗时或 NUMA 远端访问比例，也不能因交换分区曾接近满额就断定本轮发生换页瓶颈。

本轮完成了**现有配置下的顺序单请求短时基线**。未测持续负载、并发、超过 8192 token 的上下文、第二张卡双实例、重启后的图捕获回归、系统准确率，也没有独立环境新版对照。合成段落高度重复，不能代表真实会话或复杂任务。下一步若要定位长输入 TTFT，需先取得服务端阶段计时或做隔离的轻量 profiling，再按单因素测试配置候选；当前数据不足以修改 NUMA 或专家放置默认值。
